# 4단계: 회원가입·로그인 구현

작성일: 2026-11-10. 4단계 UI 작업 중 회원 인증을 먼저 연결했다. 4단계 전체나 운영 서비스가 완성된 상태는 아니다.

## 현재 동작

- 회원가입: 시험용 이메일·비밀번호·저장 안내 확인 → SQLite pending 회원 생성. 역할은 서버가 customer로 지정하며 요청의 관리자 역할은 무시한다.
- 비밀번호: 비동기 scrypt N=131072/r=8/p=1, 16바이트 무작위 salt, 64바이트 키. 원문은 저장·로그 출력하지 않는다.
- 이메일 확인: 로컬 테스트 수신함의 링크 → 확인 화면 → 버튼 POST → 30분 유효 토큰을 원자적으로 1회 소비 → active 전환.
- 로그인: 이메일·비밀번호·active 상태 확인 → HttpOnly/SameSite=Strict 개발 쿠키 → DB 세션. 세션 토큰은 DB에 해시로 저장한다.
- 내 계정: 서버 세션으로 사용자 이메일·역할 확인. 새로고침 후 로그인 유지, 로그아웃 시 서버 세션 폐기.
- 비밀번호 찾기: 로컬 수신함의 15분 유효 재설정 링크 → 새 비밀번호 → 토큰 사용 처리 및 기존 로그인 세션 전체 폐기.
- 만료: 회원 유휴 30분/절대 24시간, 관리자 유휴 15분/절대 8시간. 서버 재시작 후 쿠키를 재확인하며 수신함만 메모리에서 비워진다.
- 권한: `/api/v1/admin/session`은 서버에서 admin 역할을 확인한다. 농부 관리 화면 진입도 이 확인을 통과해야 한다.

## 실행·시험 방법

```powershell
node farmer-market/server.cjs --dev-mailbox
```

기존 화면만 제공하던 4173 서버와 충돌하지 않도록 **통합 화면·인증 서버의 기본 주소를 4175로 변경**했다.

1. [회원가입](http://127.0.0.1:4175/#register)에서 `test@example.invalid` 같은 가상 주소와 시험용 비밀번호(12~128자)를 입력한다. 다른 서비스의 비밀번호와 실제 개인정보는 사용하지 않는다.
2. [로컬 테스트 수신함](http://127.0.0.1:4175/#mailbox)에서 이메일 확인 링크를 열고 확인 버튼을 누른다.
3. [로그인](http://127.0.0.1:4175/#login) 후 [내 계정](http://127.0.0.1:4175/#account)에서 로그인 유지와 로그아웃을 시험한다.
4. 비밀번호 찾기에서도 같은 수신함의 재설정 링크를 사용한다. 새 링크 요청은 대상별 60초·시간당 5회로 제한된다.

실제 이메일·문자·외부 계정에 아무것도 보내지 않는다. `--dev-mailbox`를 생략하면 수신함은 404이며 확인 메일이 필요한 신규 가입·재설정 요청은 503으로 안내한다. 로컬 수신함은 같은 컴퓨터의 테스트 사용자가 모든 시험용 메시지를 볼 수 있으므로 실제 운영에서 활성화하지 않는다. 서버는 127.0.0.1에만 바인딩한다.

4173과 4175는 브라우저 저장소가 다르다. 이전 주소의 로컬 농부 소개·장바구니를 지우거나 자동 이관하지 않았다. 현재 농부 소개/상품/장바구니는 계속 예시·로컬 데이터이며 회원별 서버 저장은 다음 작업이다. 회원 정보와 세션만 실제 DB를 사용한다.

## 운영자 시험

공개 가입은 일반 회원만 만든다. 본인이 사용할 시험용 계정의 이메일 확인을 마친 뒤, 프로젝트 폴더에 접근 가능한 운영자가 다음 CLI로 권한을 설정한다.

```powershell
node farmer-market/backend/admin.cjs test@example.invalid
```

이 명령은 기존 active 계정만 승격하며 비밀번호를 만들거나 바꾸지 않는다. 세션을 폐기하고 감사 기록을 남기므로 다시 로그인해야 한다. 기본 관리자 계정·공유 비밀번호는 없다. 이번 작업에서 사용자의 계정을 임의로 승격하지 않았다.

농부 소개 관리의 등록·수정은 아직 브라우저 localStorage 기반이다. 서버의 농부 쓰기 API는 미구현이므로 현재 권한 확인은 화면 진입과 확인 API 범위다. 소스 코드를 조작할 수 있는 로컬 사용자의 데이터 변경을 막는 운영용 농부 CRUD 보안이 완성됐다는 의미가 아니다.

## 요청 검증·보관

- 허용 Host, 동일 Origin, 서명된 CSRF 쿠키와 헤더를 검증한다. 세션은 CSRF 해시에 연결된다. 변경 요청은 JSON만 받고 본문은 8KB로 제한한다.
- 로그인 이메일별 15분 5회, IP별 15분 15회, 인증 변경 요청 IP별 시간당 50회, 재설정/재확인 이메일별 시간당 5회 및 60초 간격으로 제한한다. 인메모리 제한이므로 다중 인스턴스·서버 재시작을 넘는 제한은 미구현이다.
- 비동기 해시 처리는 프로세스당 최대 2개로 제한한다. 가입 응답과 확인/재설정 요청 응답은 계정 존재 여부를 구별하지 않는다.
- 일반 세션·일회용 토큰은 해시만 DB에 저장한다. 개발 수신함은 실제 메일 대신 링크 원문을 메모리에 최대 30개 보관하고 서버 재시작 때 지운다.
- 입력 오류 시 이메일·폼 값을 유지하며 처리 중 버튼을 비활성화한다. 성공 후 비밀번호 입력을 비우고 확인/재설정 토큰은 주소에서 제거한다.
- 개발용 저장 안내 동의는 `consent_records`에 dev-v1으로 기록한다. 실제 판매용 이용약관·개인정보 동의 문서로 대체한 것은 아니다.

## 검증

```powershell
node farmer-market/backend/verify-auth.cjs
node farmer-market/verify-all.cjs
```

독립 메모리 DB·임시 포트에서 가입·해시·역할 주입 차단·중복 이메일·미확인 로그인 제한·확인 토큰 1회 사용·세션 분리/만료·로그아웃·재설정 후 이전 비밀번호 거절/세션 폐기·CSRF·타 Origin·관리자 권한·횟수 제한·수신함 기본 비활성화를 시험한다. 실제 DB의 브라우저 시험에는 가상 주소의 시험용 일반 회원 1개를 사용했다.

브라우저에서는 가입→수신함→이메일 확인→로그인→새로고침 후 유지→관리자 접근 차단→로그아웃을 확인했다. 비밀번호 재설정의 서버 흐름은 HTTP 통합 테스트로 검증했다.

## 남은 작업

- 농부 소개·상품·회원별 장바구니와 주문을 서버 DB에 연결하고 쓰기 API에 실제 리소스 권한·감사 기록을 적용한다.
- 실운영 HTTPS/Secure 쿠키, 실제 메일 어댑터·작업 큐·발신 도메인, 계정별 동의/탈퇴·보유 기간·정책을 연결한다. 현재 HTTP 개발 쿠키 구성을 외부 공개 배포에 사용하지 않는다.
- 주문조회·결제·농부 주문 전달·후기·상품 문의·알림 구독은 아직 서버에 연결하지 않았다.
- 운영 환경 배포 전 관리자 추가 인증, 영속적인 실패 횟수 제한, 메일/비밀번호 변경 이벤트 감사·세션 관리와 보안 종합 검수를 진행한다.

설계 근거: [Node.js 24 crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). 제한 횟수·수명·로컬 수신함은 본 프로젝트의 개발 선택이다.
